# Pull Request, форк и code review

Pull Request (PR) — это не команда Git, а механизм GitHub: «посмотрите мою ветку, можно ли влить её в main?».

## Зачем PR, если можно сразу в main

Можно, но не нужно:

- **Изменения видны целиком** — диффом, файл за файлом, с подсветкой.
- **Есть обсуждение** — комментарии к строкам кода.
- **Есть проверки** — тесты, линтеры, сборка запускаются автоматически.
- **Есть история решений** — кто согласовал, когда и почему.
- **Ничего не сломается случайно** — изменения попадают в main только после ревью.

## Путь одного изменения

```bash
git switch -c feature/avatar          # 1. своя ветка
git add . && git commit -m "feat: аватар в профиле"   # 2. коммиты
git push -u origin feature/avatar     # 3. ветка на GitHub
# 4. на сайте: "Compare & pull request" → заполнить описание → Create
# 5. коллега смотрит, комментирует, request changes или approve
# 6. Merge pull request → Delete branch
git switch main && git pull           # 7. забрать результат к себе
```

## Как писать хорошее описание PR

Шаблон, который работает:

```markdown
## Что сделано
- Добавлен аватар в профиль пользователя

## Зачем
Закрывает #42: в списке обращений просили видеть аватар

## Как проверить
1. Открыть /profile
2. Убедиться, что аватар подтянулся из GitHub

## Чек-лист
- [x] Добавил тесты
- [x] Проверил на мобильном
```

## Форк: когда у тебя нет прав на запись

Форк — это **твоя копия чужого репозитория** на GitHub. Такой путь для open source:

1. Кнопка **Fork** на странице проекта.
2. `git clone git@github.com:твой_ник/project.git`.
3. Ветка, коммиты, `push` — в свой форк.
4. PR из своего форка в исходный репозиторий.
5. Чтобы подтянуть свежие изменения из оригинала:

   ```bash
   git remote add upstream git@github.com:автор/project.git
   git fetch upstream
   git merge upstream/main
   ```

## Code review: как давать и принимать

**Если ты автор:**

- Не обижайся на замечания к коду — их пишут коду, а не тебе.
- Отвечай по существу: согласен → правка и «готово»; не согласен → объясни почему.
- Не пушим `--force` в ветку, которую уже смотрят.

**Если ты ревьюер:**

- Начинай с того, что сделано хорошо (правда, а не из вежливости).
- Различай «блокер» и «придирку»: `nit:` для мелочей — так принято.
- Объясняй причину: не «переименуй», а «переименуй, потому что это список, а не словарь».

:::tip Пять минут ревью экономят час
Если в PR больше 400 строк — проси разбить. Маленькие PR смотрят внимательнее и быстрее.
:::

## Полезные команды рядом

```bash
gh pr create --fill        # создать PR из текущей ветки (GitHub CLI)
gh pr list                 # открытые PR
gh pr checkout 42          # локально проверить чужой PR
gh pr review 42 --approve  # одобрить
```

## Мини-практика

Представь, что ты готовишь PR. В терминале ниже:

1. `git switch -c feature/profile-avatar` — ветка под задачу.
2. `echo "avatar: on" > profile.txt` — «изменение».
3. `git add .` и `git commit -m "feat: add avatar to profile"` — осмысленный коммит.
4. `git push -u origin feature/profile-avatar` — отправить ветку.
5. `git log --oneline --graph` — посмотреть, как выглядит история для ревьюера.
